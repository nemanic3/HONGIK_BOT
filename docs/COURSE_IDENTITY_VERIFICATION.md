# 과목 식별·변경 이력 후속 검증 — 2026-10-10

## 구현

기존 다중 캡처 OCR, 원본/추출/확정 JSON 분리, JWT 인증, 수정·확정 API, 졸업요건 엔진과 대시보드를 재사용했다. 기존 성적 JSON의 과목명·학점·이수구분을 카탈로그 값으로 덮어쓰지 않는다.

- `CourseIdentity`: 학수번호와 독립적인 UUID.
- `CourseVersion`: 실제 연도·학기별 학수번호, 과목명, 학점, 이수구분, 학과·캠퍼스, 문서 근거. 기존 버전은 수정하지 않는다. 동일 UUID의 속성이 달라지는 등록은 금지하며, 변경된 과목은 별도 식별자·버전과 명시적 동일과목 관계로 연결한다.
- `CourseEvidence`: 문서명, SHA-256, PDF·인쇄 페이지, 적용 문구, 공식 확인 여부·담당자·시각. 기본은 미확인.
- `CourseRelation`: 동일과목, 대체과목, 재수강 허용을 분리한다. 대체 인정은 정확한 정책 버전과 요건 ID, 방향에 한정한다. 재수강 허용만으로 필수 과목을 충족하거나 두 기록을 자동 합산하지 않는다.
- 검증된 과목 정보와 공식 확인된 관계만 과목 동일성 연결에 사용한다. 이름/별칭만으로 과목을 연결하지 않는다. 기존 정책 JSON 관계도 명시적 공식 확인 없이 연결하지 않는다.
- OCR 이후, 상세 조회, 확정, 보고서 계산에서 서버가 학수번호+실제 수강학기를 재검증한다. 이름·학점·이수구분을 교차 확인하며, 불일치·학기 누락·모호한 코드·미확인 근거는 확인 필요로 표시한다. 클라이언트가 보낸 UUID/일치 표시를 신뢰하지 않는다.
- 확인되지 않은 기존 기록은 보존한다. 기존 학수번호 기반 영역별 집계는 잠정치로 유지하지만, 과거 학기 정보 없이 현행 필수 과목을 충족했다고 확정하지 않는다. 확인 필요 상태를 유지한다.
- 같은 학수번호가 다른 과목에 재사용된 경우 공식 학기별 버전으로 구별한다. 부분적으로만 식별된 중복 코드는 임의 합산하지 않는다.
- 검토 화면에 기준 과목과 근거 페이지, 확인 필요 사유를 표시한다. 필드 수정 시 오래된 일치 표시를 취소하고, 실제 학기 수정 시 연도·학기 메타데이터도 갱신한다.
- Django 관리자에서 근거·과목·관계를 관리할 수 있다. 이력 삭제는 제공하지 않는다. 일반 학생에게 공식 관계 등록 권한을 주지 않는다.

## 근거와 미확인 범위

`docs/graduation-requirements-analysis.md`의 PDF 3/인쇄1(폐지·대체와 동일과목 구별), PDF 4/인쇄2(명칭 변경), PDF 98–99/공-10–11(컴공 과목표) 분석을 설계 근거로 사용했다. `backend/analysis/data/hongik_cs_2026.json`의 출처·초안 상태를 유지했다.

이번 작업 환경에서는 해당 2026 교과과정 PDF 원본을 찾지 못했으므로 원문 재검증을 완료했다고 주장하지 않는다. 기존 분석 문서만으로 과거 학수번호 쌍이나 적용 학기를 추측하지 않았으며, 실제 과목 변경 관계를 자동 생성하지 않았다. 새 이력 테이블은 비어 있는 상태로 마이그레이션된다. 공식 연도별 자료를 확보하여 관리자 검토 후 등록해야 자동 식별 범위가 넓어진다.

정확한 달력 학기(`2021-1`, `2025-winter` 등)를 요구한다. 학년 학기(`1-1`)에서 수강연도를 추정하지 않는다. 정책별/학과별 이수구분 별칭 역시 임의 변환하지 않는다. 대체 인정은 현재 과목군 요건에 한정하며 전공 학점 분류나 재수강 권한을 자동 변경하지 않는다. 다른 학과/캠퍼스, 전체 학기 재수강의 일괄 제외 정책은 이번 변경에서 새로 확정하지 않았다.

- 회귀 시험: 코드 재사용, 코드/학기/이름/학점/이수구분 불일치, 모호한 버전, 미확인 자료, 동일과목 중복학점 방지, 요건별 대체 인정, 재수강 허용과 동일과목의 구분, 기존 성적 보존.

## 적용 시 주의

코드 배포 전 해당 대상 DB를 백업하고 사본 검증 후 승인된 DB에 마이그레이션해야 한다. 새 코드가 새 테이블에 의존하므로 마이그레이션 없이 기존 백엔드만 재시작하면 안 된다. 공식 자료 등록 전에는 확인 필요 항목이 많은 것이 의도된 동작이다. 사용자 확인은 학교 공식 변경 관계를 생성하지 않는다.

사용자의 후속 요청으로 코드 변경을 커밋·푸시하되, 기존 로컬 DB·업로드·비밀키·백업·생성된 빌드 설정 변경은 포함하지 않는다. 기존 stash는 적용·삭제하지 않는다. 실행 환경 배포는 하지 않는다.
